## 遇到的问题

写一段往 `std::vector` 里塞十万个元素的代码，在 Windows 上跑和 Linux 上跑，`capacity()` 的变化序列不一样：

- MSVC：1, 2, 3, 4, 6, 9, 13, 19, 28...
- libstdc++（GCC）：1, 2, 4, 8, 16, 32...

同样是 `push_back`，同样是 C++ 标准库，长得完全不一样。

## 我一开始的错误理解

我以为标准规定了扩容要"翻倍"，MSVC 是特例。

翻 `[vector.capacity]` 才发现，标准从头到尾只说"均摊常数时间"，**从来没规定增长因子**。原文只要求 `push_back` 的复杂度是均摊 O(1)，具体怎么摊，实现自己定。

所以 1.5 和 2 都是合规的。

## 查到的真相

增长因子的选择，核心考虑是**能不能复用完之前释放的内存块**。

以 1.5 倍为例，随着容量增长，历史释放的块总大小：

```
旧块 1 → 新块 1.5 → 需要 1.5，前面的 1 不够
旧块 1.5 → 新块 2.25 → 需要 2.25，前面 1+1.5=2.5 > 2.25，够了
```

一旦跨过某个点，新申请的大小总能被"之前所有已释放块之和"装下（几何级数收敛）。这意味着内存分配器有机会直接在原地拼出一块连续区域，不需要真的找新地方。

而 2 倍不行：`1+2+4 = 7 < 8`，永远差一点。前面的块加起来总是刚好不够。

这就是为什么 MSVC 选 1.5（准确实现是 `max(size + 1, size * 1.5)`），libstdc++ 选 2。libstdc++ 更看重"拷贝次数少"，1.5 倍要拷贝更多次。

代价对比：1.5 倍扩容的拷贝总次数更多，但内存碎片更少；2 倍扩容拷贝少，但容易浪费。

## 结论

- 标准不保证扩容因子，**跨平台代码不能依赖 `capacity()` 的具体序列**
- 需要确定性时，先 `reserve()`，这是唯一能控制的
- `reserve` 传多了浪费内存，传少了还是要扩容，估准才是关键
- 如果非要依赖"扩容后指针不失效"，那是错的思路，任何扩容都会让迭代器失效

顺带记一个容易踩的：`reserve` 之后 `size()` 还是 0，别拿 `size()` 当可用空间。
